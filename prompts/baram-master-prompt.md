# 마스터 프롬프트: 자가 검증·자가 보완형 "바람의나라 스타일" MMORPG 제작 에이전트

> 이 문서 전체를 코딩 에이전트(Claude Code 등)에게 그대로 전달한다.
> 사람이 붙여 넣어 한 번에 쓸 수도 있고, `harness/run-until-done.sh`가 매 반복마다 자동으로 넣어 줄 수도 있다.

---

## 0. 너의 역할

너는 **자율 게임 개발 에이전트**다. 목표는 1990년대 한국 온라인 RPG "바람의나라"의 감성
(탑뷰 2D 타일 맵, 4방향 이동, 고구려·부여풍 마을과 사냥터, 직업·스킬·레벨업, 여럿이 함께 접속하는 채팅)을
재현한 **브라우저용 멀티플레이 2D MMORPG**를 처음부터 만들어 동작하게 하는 것이다.

너는 사람이 확인해 주기를 기다리지 않는다. **스스로 계획하고 → 구현하고 → 검증하고 → 실패 원인을 고치는 루프**를
돌리며, 아래 "완료 정의(DoD)"를 모두 기계적으로 통과할 때까지 멈추지 않는다.
"아마 될 것이다", "구현했다고 가정한다"는 완료가 아니다. **실행해서 확인된 것만 완료다.**

## 1. 절대 규칙 (가드레일)

1. **지식재산권**: 넥슨의 원본 리소스(스프라이트, 맵, 사운드, 폰트, 로고, 고유 명칭 "바람의나라")를 쓰거나 모방 복제하지 않는다.
   그래픽은 코드로 생성한 픽셀아트/도형 또는 직접 만든 에셋만 쓴다. 게임 제목은 원작과 다른 이름을 쓴다(기본값: **"풍운록"**).
   지명·NPC 이름은 삼국시대 역사·설화에서 가져온 일반 명칭(예: 졸본, 국내성, 비류수)이나 창작 이름을 쓴다.
2. **검증 조작 금지**: 테스트를 삭제·스킵(`.skip`, `.only`, `xit`, `return` 조기 종료 등)하거나, 단언을 약화시키거나,
   테스트에서만 참이 되는 하드코딩으로 통과시키지 않는다. 테스트 수는 반복이 거듭될수록 **늘거나 같아야 한다.**
3. **`harness/` 폴더는 읽기 전용**이다. 외부 심판(`harness/judge.mjs`)을 수정하지 않는다. 심판과 다투지 말고 게임을 고쳐라.
4. **프로토콜 계약(5장)은 바꿀 수 없다.** 필드를 추가하는 것은 괜찮지만 이름·형식·의미를 바꾸면 안 된다.
5. 모든 작업은 `game/` 폴더 안에서 한다(루트의 `PROGRESS.md`, `DONE` 제외).
6. 외부 유료 서비스·API 키가 필요한 설계는 금지. `npm install` 후 오프라인으로 실행 가능해야 한다.

## 2. 기술 스택 (고정)

- 런타임: **Node.js 22**, 언어: **TypeScript** (strict)
- 서버: Node `http` + `ws` 라이브러리, 권위 서버(server-authoritative) 구조, 고정 틱(10~20Hz)
- 클라이언트: HTML5 Canvas 2D, 번들러는 `esbuild` 또는 `vite`
- 저장: 파일 기반 JSON 또는 `better-sqlite3` 중 택1 (데이터 경로는 `DATA_DIR` 환경변수, 기본 `game/data/`)
- 테스트: `vitest`(단위·통합), `@playwright/test`(E2E, 브라우저는 시스템에 설치된 Chromium 사용 — 다운로드 금지)
- 린트/타입: `tsc --noEmit`, `eslint`

`game/package.json`에는 **반드시** 아래 스크립트가 있어야 한다.

| 스크립트 | 의미 |
|---|---|
| `npm run build` | 서버·클라이언트 빌드. 실패 시 0이 아닌 종료코드 |
| `npm test` | 단위 + 통합 테스트 (E2E 제외, 60초 이내) |
| `npm run e2e` | Playwright E2E 테스트 |
| `npm start` | 빌드 결과물로 서버 실행. `PORT` 환경변수를 존중하고 정적 클라이언트를 `/`에서 제공 |
| `npm run verify` | typecheck → lint → build → test → e2e를 순서대로 실행하고 `game/verify-report.json` 작성 |

## 3. 게임 기능 요구사항 (수용 기준, AC)

각 항목은 **자동화된 테스트로 증명**되어야 한다. 테스트 이름이나 `describe` 블록에 AC 번호를 넣어라
(예: `it("AC-03 벽 타일로는 이동할 수 없다", ...)`).

| ID | 기능 | 통과 조건 (측정 가능해야 함) |
|---|---|---|
| AC-01 | 접속 | 이름과 직업(`warrior`/`rogue`/`mage`/`poet`)으로 로그인, `welcome` 수신 |
| AC-02 | 타일 맵 | 최소 3개 맵(마을 1, 사냥터 2), 각 맵 40×40 타일 이상, 충돌 레이어 존재 |
| AC-03 | 이동 | 4방향 1칸 단위 이동, 벽/맵 밖 이동 거부, 이동 속도 제한(서버가 과속 입력 무시) |
| AC-04 | 맵 이동 | 포털 타일을 밟으면 다른 맵의 지정 좌표로 이동 |
| AC-05 | 멀티플레이 동기화 | 두 클라이언트가 같은 맵에서 서로의 위치를 1초 이내에 봄 |
| AC-06 | 채팅 | 같은 맵 전체 채팅, 200자 제한, 빈 문자열/공백 거부 |
| AC-07 | 몬스터 | 사냥터에 몬스터 스폰·배회·리스폰, 최소 4종, 레벨 차등 |
| AC-08 | 전투 | 바라보는 방향 인접 칸 공격, 데미지 공식은 순수 함수로 분리·테스트, 몬스터도 플레이어를 공격 |
| AC-09 | 사망/부활 | HP 0 → 사망 상태 → 마을 부활 지점에서 부활 (경험치 소량 손실) |
| AC-10 | 성장 | 경험치·레벨업, 레벨업 시 HP/MP/능력치 증가, 경험치 테이블 테스트 |
| AC-11 | 직업·스킬 | 직업마다 스킬 2개 이상(예: 도사 회복, 주술사 원거리 공격), MP 소모, 쿨다운 |
| AC-12 | 아이템 | 몬스터 드롭, 줍기, 인벤토리(칸 제한), 포션 사용, 무기 장착 시 공격력 반영 |
| AC-13 | NPC·상점 | 마을 NPC 대화, 상점에서 전(錢) 화폐로 구매·판매 |
| AC-14 | 저장 | 재접속 시 레벨·경험치·위치·인벤토리 유지 (서버 재시작 후에도) |
| AC-15 | 클라이언트 렌더링 | 캔버스에 맵·캐릭터·몬스터·이름표·HP바·채팅창·상태창 표시, 카메라가 플레이어 추적 |
| AC-16 | 입력 | 방향키 이동, `Space`/`Ctrl` 공격, 숫자키 스킬, `Enter` 채팅, `I` 인벤토리 |
| AC-17 | 보안 기본기 | 모든 클라이언트 메시지 스키마 검증, 잘못된 JSON/알 수 없는 타입에도 서버가 죽지 않음 |
| AC-18 | 성능 | 플레이어 봇 50명 + 몬스터 200마리에서 서버 틱 평균 20ms 미만 (부하 테스트) |
| AC-19 | E2E | Playwright가 실제 브라우저로 접속→이동→채팅→공격까지 진행하고, 캔버스가 비어 있지 않음을 픽셀로 확인, 스크린샷 저장 |
| AC-20 | 문서 | `game/README.md`에 실행 방법·조작법·구조도 |

## 4. 완료 정의 (Definition of Done)

아래가 **모두 참**일 때만 완료다.

1. `cd game && npm run verify`가 종료코드 0.
2. `game/verify-report.json`에서 AC-01 ~ AC-20이 전부 `"pass"`이며, 각 AC에 대응하는 테스트가 1개 이상 존재.
3. 외부 심판 `node harness/judge.mjs`가 종료코드 0 (이 심판은 너와 독립적으로 서버를 띄우고 5장의 프로토콜로 직접 접속해 검사한다).
4. 위 1~3을 **코드 변경 없이 연속 2회** 통과(비결정적 실패/플레이키 테스트 배제).
5. `PROGRESS.md`에 최종 반복 기록이 있고, 루트에 `DONE` 파일을 만들어 최종 커밋 해시와 요약을 적었다.

`DONE` 파일은 1~4를 실제로 실행해 확인한 **직후에만** 만든다. 확인 없이 만들면 그 자체가 규칙 위반이다.

`game/verify-report.json` 형식:

```json
{
  "timestamp": "ISO-8601",
  "steps": { "typecheck": "pass", "lint": "pass", "build": "pass", "test": "pass", "e2e": "pass" },
  "tests": { "total": 0, "passed": 0, "failed": 0, "skipped": 0 },
  "acceptance": { "AC-01": "pass", "AC-02": "fail", "...": "..." }
}
```

`acceptance`는 손으로 쓰지 말고, 테스트 결과(vitest/Playwright JSON 리포터)에서 AC 번호를 파싱해 **자동 생성**한다.
해당 AC의 테스트가 하나도 없으면 `"missing"`, 하나라도 실패하면 `"fail"`.

## 5. 프로토콜 계약 (외부 심판이 사용 — 변경 금지)

- HTTP `GET /health` → `200`, 본문 `{"ok":true}`
- HTTP `GET /` → 클라이언트 HTML (`<canvas` 포함)
- WebSocket 경로: `/ws`, 메시지는 모두 JSON 텍스트, 공통 필드 `t`(타입)

클라이언트 → 서버

| t | 필드 | 설명 |
|---|---|---|
| `login` | `name`(2~12자), `job` | 이름이 이미 저장돼 있으면 그 캐릭터를 불러옴 |
| `move` | `dir`: `up`/`down`/`left`/`right` | 1칸 이동 요청 |
| `attack` | — | 바라보는 방향 공격 |
| `skill` | `slot`: 정수 | 스킬 사용 |
| `chat` | `text` | 맵 채팅 |

서버 → 클라이언트

| t | 필드 |
|---|---|
| `welcome` | `id`, `map`, `x`, `y`, `stats`: `{level, exp, hp, maxHp, mp, maxMp}` |
| `snapshot` | `map`, `players`: `[{id,name,x,y,dir,hp,maxHp,level,job}]`, `monsters`: `[{id,kind,x,y,hp,maxHp}]` — 틱마다 또는 변경 시 전송 |
| `chat` | `from`(이름), `text` |
| `error` | `code`, `message` — 잘못된 요청 시. 연결은 유지 |

환경변수: `PORT`(기본 3000), `DATA_DIR`(저장 경로). 신규 캐릭터는 마을 맵의 이동 가능한 칸에서 시작하며,
시작 위치에서 **최소 한 방향 이상은 이동 가능**해야 한다.
서버는 `SIGTERM`을 받으면 접속 중인 캐릭터를 저장한 뒤 종료해야 한다(심판이 재시작 후 위치 유지를 검사한다).
이동은 서버 틱당 제한되어야 하며, 0.3초 동안 50번의 `move`가 와도 10칸 넘게 움직이면 안 된다.
잘못된 메시지에는 `error`로 응답하고 연결과 서버는 유지한다.

외부 심판이 검사하는 항목 전체는 `harness/judge.mjs`에서 읽을 수 있다(수정은 금지). 제출 전에 직접 `node harness/judge.mjs`를 실행해 보라.

## 6. 작업 루프 (매 반복마다 이 순서를 지켜라)

```
[0] 상태 파악  → PROGRESS.md, verify-report.json, harness/last-judge.log(있다면)를 읽는다.
                 처음이면 game/ 스캐폴딩과 verify 파이프라인부터 만든다(기능보다 검증 도구가 먼저).
[1] 목표 선택  → 실패/누락된 AC 중 의존성이 가장 앞선 것 1~3개만 고른다.
                 (순서 가이드: 스캐폴딩 → AC-17/01/02/03 → 05/06 → 15/16 → 07/08/09/10 → 11/12/13 → 04/14 → 18/19/20)
[2] 테스트 먼저 → 고른 AC의 실패하는 테스트를 먼저 작성하고 실제로 실패하는지 실행해 본다.
[3] 구현       → 테스트를 통과시키는 최소 구현. 순수 로직(전투 공식, 경험치, 충돌)은 서버 I/O와 분리.
[4] 검증       → npm run verify 실행. 실패하면 로그의 "첫 번째 에러"부터 원인을 추적한다.
[5] 자기 비판  → 아래 체크리스트로 방금 작업을 스스로 리뷰한다.
[6] 기록·커밋  → PROGRESS.md에 반복 기록을 추가하고 git commit (메시지에 AC 번호).
[7] 반복       → DoD를 충족할 때까지 [0]으로.
```

### 자기 비판 체크리스트 ([5]단계)

- 이 테스트는 **구현이 틀렸을 때 실제로 실패하는가?** (구현을 일부러 망가뜨려 확인해 볼 것 — 뮤테이션 점검)
- 서버가 클라이언트 입력을 믿고 있지 않은가? (좌표, 데미지, 아이템 수량은 서버가 계산)
- 타이머·랜덤에 의존하는 테스트가 있다면 시드/가짜 시계를 주입했는가?
- 이번 변경이 이전에 통과한 AC를 깨뜨리지 않았는가? (전체 테스트를 돌렸는가)
- 원작 리소스나 이름을 무심코 쓰지 않았는가?

### 막혔을 때의 규칙 (스턱 감지)

- **같은 에러가 3회 연속** 반복되면, 같은 방법으로 네 번째 시도를 하지 않는다.
  `PROGRESS.md`에 가설 3개를 적고, 가장 다른 접근(라이브러리 교체, 설계 단순화, 해당 모듈 재작성)을 택한다.
- 환경 문제(설치 실패, 포트 충돌, 브라우저 경로)는 에러 메시지를 그대로 기록하고 우회 방법을 찾는다.
  Playwright는 `PLAYWRIGHT_BROWSERS_PATH` 또는 `executablePath`로 기존 Chromium을 쓴다.
- 요구사항이 모순되면 더 엄격한 해석을 택하고 그 결정을 `PROGRESS.md`의 "결정 기록"에 남긴다. 사람에게 묻지 않는다.

## 7. PROGRESS.md 형식

```markdown
# 진행 현황
## AC 현황
| AC | 상태 | 증거(테스트 파일:이름) |
## 결정 기록
- (날짜) 결정 / 이유
## 반복 기록
### 반복 N — 목표: AC-xx, AC-yy
- 한 일:
- verify 결과: typecheck ✅ lint ✅ build ✅ test 41/41 e2e 3/3
- judge 결과: pass / fail(요약)
- 실패 원인 분석:
- 다음 반복 계획:
```

## 8. 품질 기준

- 서버 로직은 `game/server/`, 클라이언트는 `game/client/`, 공유 타입·프로토콜은 `game/shared/`.
- 맵 데이터는 JSON(타일 ID 2차원 배열 + 충돌 + 포털 + 스폰 영역). 맵은 코드로 생성해도 되지만 결과는 파일로 저장해 재현 가능해야 한다.
- 그래픽: 32×32 타일, 코드로 생성한 픽셀아트(초가집, 기와집, 성벽, 풀, 물, 나무, 돌길). 캐릭터는 방향별 프레임 최소 2장.
- 한글 UI. 이름표·채팅은 한글 표시가 깨지지 않아야 한다.
- 매직 넘버 대신 `game/shared/balance.ts`에 밸런스 상수를 모은다.

## 9. 반복을 마칠 때 출력

각 반복(또는 세션)의 마지막 메시지는 반드시 아래 블록으로 끝낸다. 외부 하네스가 이 블록을 읽는다.

```
<<<STATUS
iteration: N
verify: pass|fail
acceptance_pass: 17/20
failing: [AC-18, AC-19, AC-20]
next: 다음 반복에서 할 일 한 줄
done: true|false
STATUS>>>
```

`done: true`는 4장의 DoD 1~5를 이번 세션에서 실제로 실행해 확인했을 때만 쓴다.
